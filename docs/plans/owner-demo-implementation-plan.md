## 1. 목표와 범위

**소유주가 PC와 폰에서 장비를 찾고, 계약·담당자·현재 상태를 확인하고, 같은 호기의 영상과 서류를 열 수 있는 데모를 만든다.** 화면의 디자인 완성도와 사용자 과제의 성공을 함께 검증한다.

- 업무 화면 6개: 운영 현황 / 보유 장비 / 호기 상세 / 영상 / 장비 서류 / 이상·점검 알림.
- 공통 진입 1개: 소유주 전용 설명·일상 운영 미리보기·‘데모 시작하기’ 단일 버튼.
- 메뉴 4개: 운영 현황 / 보유 장비 / 알림 / 서류. 상세·영상은 장비에 종속된다.
- WEB과 A4 PWA 모두 같은 6개 업무를 제공한다. **논리 화면 7종, 두 앱의 화면 구현 14개**를 계획 기준으로 삼는다. 이는 기존 화면 재사용을 포함한 수이며 신규 SSOT 화면 14개를 뜻하지 않는다.
- WEB도 390px에서 사용 가능하게 만든다. WEB 반응형 성공을 A4 PWA 구현 완료로 대체하지 않는다.
- 시연용 데이터·대체 영상·샘플 문서로 검증한다. 실인증·실장비 인입·영상 중계·서버 저장/삭제 정책의 검증은 별도다.

관련 문서: [화면 정의서](owner-demo-screen-review.md), [디자인 진단](../design/OWNER-DEMO-DESIGN-REVIEW-2026-09-11.md), [소유주 모의 의견](../design/OWNER-PERSONA-FEEDBACK-2026-09-11.md), [METHOD](../../METHOD.md), [QA](../QA.md).

이번 작업의 산출물은 이 실행 계획과 연결 문서다. 정식 spec·SSOT 변경, 제품 코드 구현, PR·배포·고객 전달을 수행한 것으로 기록하지 않는다.

## 2. 유지할 판단과 확인이 필요한 경계

### 설계 기준

1. 현장/호기 검색 → 계약·담당자 확인이 기본 과제다. 정상 장비·보관 장비도 검색된다.
2. 전체 보유 수와 투입/보관 구성을 하나로 보여주고, 이상은 별도의 확인 목록으로 보여준다. 가동률·타설량은 정의와 데이터가 있는 상세에서 다룬다.
3. 지도 면적과 영상 우선 행동을 고정하지 않는다. 상세 상단에서 계약·담당자를 바로 찾는다.
4. 문서명·호기·현장은 읽을 수 있는 계층으로 배치한다. 원문 미리보기와 영상 자체에 충분한 공간을 준다.
5. 최신 정보·마지막 수신 정보·미연동·미장착·조회 실패를 구분한다. 과거 측정값·위치를 현재 정상 상태처럼 표시하지 않는다.
6. 진입 미리보기에 정상 운영과 계약 정보도 포함한다. 현재 v2 정적 시안은 배치 참고이며 최종 구현 증거가 아니다.

| 항목 | 데모에서 사용할 기준안 | 확인·확정 범위 |
|---|---|---|
| 보관·단말기 탈부착 | 배치 상태와 통신 상태를 별도 축으로 표시하는 샘플. 미장착을 수신 장애로 집계하지 않음 | 실제 기록 주체·재장착·알림 억제는 DISC-059. FR-043의 계약·운영 확정으로 처리하지 않음 |

실제 고객이 결정해야 하는 부분만 해당 작업에서 대기한다. 원문 대조·시안·샘플 열람·UI 검증은 계속 진행할 수 있다. 모의 페르소나 의견을 DISC의 고객 승인 기록으로 사용하지 않는다. 신규 범위는 기존 DISC 중복 여부를 확인한 뒤 open으로 등록하며, 이 표는 별도 결정 원장이 아니다.

## 3. 구현 전 명세·라우트 정리

### 3.1 경로 기준안

아래 신규 경로는 **구현 설계안**이다. OD-01에서 기존 레지스트리와 충돌을 확인하고 `/ssot`로 ID를 채번한다. 이 문서만 보고 미등록 `data-scr`나 화면 상수를 만들지 않는다.

| 논리 화면 | WEB 기준안 | A4 PWA 기준안 | 명세 처리 |
|---|---|---|---|
| 소유주 진입 | `/login?demo=owner` — B0-01의 소유주 전용 진입 상태 | `/a4/login` — A4-01 | 고객용 URL에는 역할 카드 없음. 공통 역할 로그인은 기존 내부 검증 경로로 유지 |
| 운영 현황 | `/b1/dash` — B1-02의 owner 구성 | `/a4/overview` 신규 | owner 홈을 이 현황으로 연결. 기존 제조사 뷰의 요구는 역할별로 명시 |
| 보유 장비 | `/b1/fleet` 신규 | `/a4/fleet` — A4-02 재사용 | A4-02의 가용 자동 판정까지 구현했다고 해석하지 않게 제목·범위를 정리 |
| 호기 상세 | `/b1/fleet/[device]` 신규 | `/a4/fleet/[device]` 신규 | 주소 진입·뒤로가기·대상 권한 검사 포함 |
| 영상 | `/b1/fleet/[device]/video` 신규 | `/a4/fleet/[device]/video` 신규 | 기존 B1-02M의 플레이어·미디어 로직 재사용. 소유주용 전체 뷰를 기존 모달 경로에 억지로 매핑하지 않음 |
| 장비 서류 | `/b1/docs?device=…` — B1-05의 owner 구성 | `/a4/docs?device=…` 신규 | 기존 A4-06 ‘운전자 서류’와 구분. 문서 선택·첨부는 등록된 화면의 상태로 처리 |
| 이상·점검 알림 | `/b1/alerts` 신규 | `/a4/alerts` 신규 | 장비/알림 선택을 쿼리로 유지. B1-03 요청 수신함과 분리해 무관한 승인 폼 노출 방지 |

고객 데모의 WEB 기본 진입은 소유주 전용 URL이다. 미로그인 상태에서 소유주 전용 페이지에 접근하면 그 진입점으로 복귀한다. `/login?demo=owner`는 보기 선택일 뿐 권한 부여 수단이 아니며, 실제 세션의 ownerId로 데이터를 제한한다. 유효한 다른 역할 세션을 URL만으로 소유주 세션으로 덮어쓰지 않는다. ‘데모 시작하기’를 눌렀을 때만 명세에 정한 데모 계정으로 시작한다.

필터·선택 호기·문서·알림·재생 모드는 URL 또는 명시한 탐색 상태로 보존한다. URL 이동은 기존 `state/capture/scene` 조건을 보존하고, 복귀 주소는 해당 앱 내부의 허용된 경로로 한정한다. PWA→WEB 리디렉션으로 상세를 대신하지 않는다.

소유주 4개 메뉴는 데모 대상·역할 기준으로 원천에 정의해 생성한다. 공유 B1 화면의 전역 nav 설정을 바꿔 제조사 메뉴까지 지우지 않는다. 새로운 메뉴 범위 필드가 필요하면 스키마·검사·생성을 같은 작업에서 갱신한다.

기능 명세는 `specs/owner-experience/{spec,design,tasks}.md`에 묶고, 기존 spec에는 해당 역할의 변경점을 반영한다. 새 화면 등록 → FR/IF/엔티티/상태 연결 → spec 초안 → 명세 검사·재생성 순서다. 원문에 없는 운영 규칙은 데모 가정 또는 미결로 표시한다.

데이터 형태·집계·수신 상태·스코프는 domain/API 계약으로, 시연 세트는 mock으로, 표시 컴포넌트는 ui로 나눈다. 두 앱은 동일 계약을 소비하고 apps끼리 import하지 않는다. ui가 mock을 직접 읽거나 페이지가 별도 집계·상태 판정을 복제하지 않는다. API 반환 복사·변경 입력 snapshot 등 기존 경계 규약도 유지한다.

## 4. AI 작업 루프와 책임

```text
원문·기존 구현 대조 → SSOT·spec·검증 계획 → 화면 구조·공통 패턴
 → 작은 구현 단위 → 해당 AC 검사 → 독립 코드·화면 리뷰
 → 수정·재검사 → PR·CI → 병합 → 통합 시연·문서 생성 → 고객 검토
```

| 역할 | 책임 | 제출할 증거 |
|---|---|---|
| 주 에이전트 | 범위·의존성·명세 통합, 한 작업 단위 구현, 결과와 미결 관리 | 변경 목록·AC 대응·계획 갱신 |
| reviewer | spec 대조·스코프·경계·토큰·쿼리·회귀 검토. 구현자 주장만으로 판정하지 않음 | AC별 충족/미충족/확인 불가, 파일:줄, PR 전 ‘머지 가능/불가’ |
| verifier | 빌드·명령·실제 브라우저·캡처·데이터 대조 | exit code·로그·실제 역할·상태·화면·실패 재현 |
| 소유주 역할 검토 | 장비 찾기·계약/담당자·서류·영상의 실제 과제 관점 검토 | 관찰과 가설. 실제 고객 승인으로 사용하지 않음 |
| 사용자 / 고객 | 의도·실제 업무 규칙·범위·고객 검토·공개 판단 | 기존 결정 원장의 결정 또는 검토 기록 |

한 작업은 한 branch/PR로 진행한다. 제품 화면 변경은 PR당 최대 3개이며, 수정 범위가 넘으면 쪼갠다. 공통 컴포넌트 변경은 파급 화면을 별도로 나열한다. 기본은 순차 실행이고, 병렬화할 경우 데이터·컴포넌트 계약이 고정된 뒤 겹치지 않는 파일을 worktree로 분리한다. 포트·캡처 출력 디렉터리를 공유하는 검증은 병렬 실행하지 않는다.

### 작업별 AI 지시서에 반드시 포함할 항목

```text
작업: OD-xx / base SHA / 현재 검증할 diff
목표: 사용자가 완료할 한 가지 과제
근거: 원문 셀·정식 FR/SCR·spec AC·미결 DISC
수정 허용: 파일·패키지·라우트, 공유 파일 담당자
유지 조건: 다른 역할·기존 데모·쿼리·스코프·토큰 경계
데이터: 세트/소유주/호기/시각/오류 상태
검증: 명령·기대값·화면 폭·테마·증거 경로
반환: 변경 요약·AC별 결과·로그/캡처·미확인 사항
```

새 세션/에이전트는 명세와 마지막 검증 결과부터 이어받는다. 상태는 `계획 / 구현 중 / 검증 대기 / 수정 필요 / 검증 통과 / 고객 확인 대기`로 기록한다. ‘테스트 작성’·‘코드 생성’·‘시안 있음’을 검증 통과로 올리지 않는다.

중간 PR의 검증 대상은 그 작업에 해당하는 AC와 회귀 범위다. 아직 구현하지 않은 후속 화면은 ‘검증 대기’로 남기고, 연결 링크는 실제 대상이 준비될 때 활성화한다. OD-13에서는 이 중간 상태를 허용하지 않으며 6개 업무 흐름의 필수 기능·이동이 모두 동작해야 한다.

각 화면 PR에는 `pnpm verify`, `pnpm build`, 관련 e2e, 해당 화면·상태 캡처와 육안 확인이 들어간다. 최종 PR에는 전체 회귀를 실행한다. 명세·토큰 원천 변경이 있으면 `ssot:build`·`tokens:build` 생성물을 함께 반영한다. `Refs`는 등록 완료된 실제 FR/SCR만 사용한다.

기존 `current_wave` 밖의 새 화면은 스케줄 정보와 구현 검증 대상을 구분해 관리한다. 등록 단계의 자리 화면을 완료로 세지 않고, owner 데모 검증은 명시한 전체 대상에 대해 별도로 실패/미구현을 보고한다. 전체 플랫폼의 4웨이브 승격은 이번 작업의 선행 조건이 아니다.

## 7. 테스트 데이터와 검증 오라클

### 데이터 세트

| 세트 | 구성 | 필요한 이유 |
|---|---|---|
| 기본 시연 | 소유주 A의 5대. 정상·이상·점검·수신 중단·보관/미장착 예시, 계약/담당자·장비 파일·용도별 영상 | 모든 화면에서 같은 5대를 찾고 5분 과제를 수행 |
| 다른 소유주 | 소유주 B의 별도 호기·문서·카메라·알림·계약·담당자. A와 구분 가능한 내용 | 데이터 1소유주만으로 스코프 통과라고 주장하지 않기 |
| 경계 상태 | 배치 미확인, 계약/담당자 미등록, 부분 수신, 계측 미연동, 부품 기준 없음, 복수 알림, 위치 없음 | 0/정상/가용으로 잘못 해석하지 않는지 확인 |
| 파일·영상 | 호기 식별이 가능한 서로 다른 PDF/이미지, 손상/없음, 알려진 길이의 무음 클립, 실시간 대체·스냅샷·미확보 | 파일명·배지만 표시하는 가짜 성공 검출 |
| 대량 탐색 | 명시적으로 ‘규모 검토용’인 120대 합성 세트, 긴 현장/문서명, 다수 필터 결과 | 목록·검색·정렬·레이아웃·응답 시간 확인. 기본 5대 데모와 합산하지 않음 |

새 데모 데이터는 기존 제조사·현장 데모의 고정 5대 시드를 무조건 덮어쓰지 않는다. 별도 시연 세트로 선택하되, ordinary session에서도 데모의 같은 세계가 유지되도록 데이터 부트 기준을 명세한다. `capture=1`이나 페이지별 `state`가 바뀔 때 호기·회사·계약이 다른 세트로 바뀌지 않아야 한다.

오라클은 명세에 적힌 장비 구성·소유주 매핑·파일 내용·클립 길이·시각이다. 화면의 집계 함수나 `HOME_OF` 같은 구현 상수를 기대값으로 재사용하지 않는다. 예: A=5대/B=별도 장비라면 A의 검색·요약·지도·직접 API에서 B가 0개인지 각각 확인한다.

첨부 성공은 파일 메타데이터만으로 판정하지 않는다. 읽을 수 있는 원문·호기 연결·세션 목록 반영을 확인하고, 취소·잘못된 형식·읽기 실패·오프라인에서는 성공 이력을 만들지 않는다. 크기·형식 허용값은 기존 정책을 재사용하거나 spec에 시연용 값으로 명시한다.

### 8.2 반응형·시각 검사 조합

| 대상 | 필수 폭·높이 | 테마 | 기본 검사 |
|---|---|---|---|
| WEB | 1280×842, 1024×842, 768×842, 390×800 | light·dark | 진입+6개 업무 화면, 검색·상세·뷰어의 접근 가능성 |
| PWA | 375×800, 390×800, 430×900, 768×1024 | light·dark | 같은 7종, 하단 메뉴·48px 터치·가로 회전/넓은 화면 재배치 |

기본 상태는 **7종×2앱×4폭×2테마=112조합**을 계획 기준으로 한다. 실제 정식 화면·상태·앱을 등록한 뒤 원천에서 대상 목록을 생성하고 실측 건수를 보고한다. 기본 조합 외에 빈/조회 실패/오프라인/미수신/다수 알림/파일·영상 실패/첨부·뷰어 열림은 WEB 1280·PWA 390에서 필수로 검사한다. 공통 컴포넌트가 영향을 주면 해당 폭·테마로 추가한다. 모든 상태를 무조건 전체 폭에 곱하지 않는다.

각 캡처에서 실제 role·ownerId·호기·데이터 세트·시각·화면 ID·URL·viewport·theme·source SHA를 기록한다. WEB의 B1 기본 역할 `control`로 찍힌 캡처를 소유주 화면 증거로 세지 않는다. 첫 뷰포트와 전체 내용/뷰어를 필요에 따라 별도로 확인하며, 기본 화면을 캡처했다고 열린 파일·알림 상세까지 검증한 것으로 세지 않는다.

시각 통과 기준은 다음과 같다.

- 필수 제목·호기/현장·계약/담당자·문서명·상태·주 행동이 잘리지 않는다. 문서명·현장명은 의미에 따라 2줄 이상 읽을 수 있게 한다.
- 페이지 가로 넘침, 240px 고정 메뉴로 인한 본문 압축, 상세가 숨겨져 사라지는 현상이 없다. 표 내부 스크롤이 필요하면 별도로 지정한다.
- 운영 현황 첫 화면에 검색·전체 장비 접근·운영 구성·우선 확인 경로가 있고, KPI가 반복돼 주 콘텐츠를 밀지 않는다.
- 정상/이상/미수신이 색 이외의 글자·형태로 구분된다. 중요한 시각·문서명은 작은 회색 보조문에 묻히지 않는다.
- 키보드 확대 200%, 작은 폭의 닫기·복귀, PWA 터치, 모달 포커스 복귀를 확인한다.
- 기존 QA의 대비 본문 7:1·보조 4.5:1·UI 3:1, 터치 WEB 44px·PWA 48px, 최소 글자 12px 기준을 적용한다. 화면 수를 줄이기 위해 기준을 낮추지 않는다.
- 단순히 화면이 비어 있다는 이유로 장식 KPI·카드를 추가하지 않는다. 지도·영상·원문이 실제로 보이는지 확인한다.

owner 전용 캡처·결과는 전용 디렉터리와 매니페스트에 저장한다. 기존 `shots/manifest.json`은 전체 계약 문서용이므로 부분 캡처 결과로 덮어쓰지 않는다. 새 검증기의 인터페이스·실행 명령은 OD-03에서 package script와 함께 등록한다. 이 계획에 적은 신규 테스트명·도구 경로는 현재 존재하는 명령이 아니다.

### 8.4 성능·자원 내부 기준안

계약 SLA가 아닌 로컬 데모 검토 예산으로, OD-00에서 Node·브라우저·기기·데이터·캐시 조건을 기록한다. 120대 mock 세트에서 준비 5회 후 20회 측정하고 p50/p95를 남긴다. 이미 데이터가 로드된 검색·정렬의 입력→결과 갱신은 p95 300ms 이하, mock 데이터 기반 상세 콘텐츠 표시는 p95 1초 이하를 목표로 한다. 외부 지도 타일·실스트림 네트워크 시간을 이 값으로 보증하지 않는다.

초과하면 원인과 UX 영향을 기록해 최적화하거나 명세의 예산을 근거와 함께 재검토한다. AI가 검사 통과를 위해 조용히 기준을 느슨하게 바꾸지 않는다. 영상/PDF를 반복해서 열고 닫은 뒤 재생 중 video·중복 구독·불필요 objectURL이 남지 않는지 확인한다. 외부 타일 실패는 목록 대체 경로를 검사하고, 정상 지도 시연 증거도 별도로 확보한다.

## 9. 실행 명령과 증거 관리

### 현재 저장소에 있는 명령

저장소 절대 경로에서 각 명령의 exit code를 직접 확인한다. 아래는 게이트 목록이며 한 번에 병렬 실행하는 스크립트가 아니다. preview 포트를 쓰는 작업은 순차로 실행한다.

```sh
cd /Users/adminvia/devwork/_DY/boomeyes && pnpm ssot:check
cd /Users/adminvia/devwork/_DY/boomeyes && node tools/ssot/check.mjs --specs
cd /Users/adminvia/devwork/_DY/boomeyes && node tools/ssot/check.mjs --docs
cd /Users/adminvia/devwork/_DY/boomeyes && pnpm verify
cd /Users/adminvia/devwork/_DY/boomeyes && pnpm build
cd /Users/adminvia/devwork/_DY/boomeyes && pnpm e2e
cd /Users/adminvia/devwork/_DY/boomeyes && pnpm capture --dark --strict
cd /Users/adminvia/devwork/_DY/boomeyes && pnpm capture:compare
cd /Users/adminvia/devwork/_DY/boomeyes && pnpm design:audit:color
```

기존 spec·문서만 수정하는 계획 단계에는 문서/spec 검사와 diff 검사를 우선한다. 구현을 시작한 뒤 변경 종류에 맞는 게이트를 실행하고, 필수 단계가 빠진 최종 결과는 통과로 보고하지 않는다.

owner 전용 실제 e2e는 OD-03에서 `tests/e2e/web-owner-*.spec.ts`, `pwa-owner-*.spec.ts` 계열로 추가한다. 현재 Playwright의 `web-*.spec.ts`/`pwa-*.spec.ts` 패턴에 맞춰 CI가 자동 발견하도록 한다. 동적 테스트 생성 결과가 0건이면 실패하도록 집계한다. 로그인/스코프·연속 과제·시각 재현 테스트는 파일 또는 describe 단위로 구분한다.

추적 매핑과 결과는 테스트/원천에서 생성한다. 최소 필드: `task, ac, scr, role, dataset, state, viewport, theme, sourceSha, command, exitCode, expectedCount, actualCount, status, evidence, reviewer`.

증거 묶음에는 다음을 남긴다.

- 명령 로그와 요약(성공/실패/skip·예상/실행 건수). 필수 skip·환경 차이·0건 실행은 통과로 처리하지 않음.
- 실패 시 Playwright trace·스크린샷·콘솔/요청 오류·재현 URL. 재실행으로 지나가도 flaky 원인과 최초 실패를 보존.
- 실제 원문/영상·전체/첫 뷰포트·중요 상태 캡처. 같은 파일명으로 다른 빌드 증거를 덮어쓰지 않음.
- base/head SHA·working tree diff 해시·의존성·OS·폰트·Playwright·DPR·시간대. 미커밋 검토와 최종 커밋 결과 구분.
- reviewer의 AC 대조와 화면 판단. 모델의 ‘좋아 보임’만으로 판정하지 않음.

포트 4173/4174를 확인하고 자기 작업이 시작한 서버만 종료한다. `pnpm e2e`가 기존 서버를 재사용할 수 있으므로 남은 옛 빌드에서 검사하지 않게 한다. 게이트 출력은 파이프로 가리지 않으며, 셸 체인의 실패를 무시하지 않는다.

| G1 명세 준비 | SSOT 등록·실제 AC·검증 매핑·기존 명세 충돌 해소 | 원천/spec으로 복귀. 테스트가 없도록 요구를 삭제하지 않음 |
| G2 데이터·패턴 준비 | 스코프/집계 단위 검사와 공통 패턴·실행 가능한 검증 도구 준비 | domain/mock/패턴 지침 수정 |
| G3 작업 단위 구현 | 해당 AC·폭·상태·실콘텐츠 검사, verify·build·관련 e2e 통과 | 같은 작업에서 재현·수정·영향 검사. 다음 작업이 실패를 숨기게 하지 않음 |
| G4 독립 리뷰·PR | reviewer ‘머지 가능’, 사람 리뷰, exact head CI 통과·의도된 시각 차이 확인 | AC 미충족/확인 불가는 수정·증거 보강 후 재리뷰 |
| G5 전체 통합 | VT-01~12의 필수 내부 검사·대상 커버리지·다른 역할 회귀 통과 | 실패 원인별 작은 수정 작업. 관련 검사와 최종 통합 재실행 |
| G6 고객 검토 준비 | 동일 빌드 문서·5분 데모·명시한 제약·내부 소유주 과제 리허설 준비 | 실제 앱·문서·대본의 불일치를 수정 |
| G7 실제 고객 확인 | 고객이 과제 수행·의견 확인, 필요 결정 기록 | 고객 의견을 spec/원장에 반영 후 해당 검사로 복귀. AI 모의 의견으로 대체하지 않음 |
| G8 공개·인계 | 구체적 결과에 대한 사용자 승인, 배포/전달·복구·외부 접근 점검 | 공개 보류. 로컬 검증 결과와 외부 환경 미확인을 구분 |

예상된 시각 변경은 실패 이미지를 먼저 검토한 후 **CI의 baseline workflow**로 갱신한다. 로컬 macOS 기준선을 CI Ubuntu와 비교하거나, 실패를 지우려고 자동 accept하지 않는다. 현재 기준선이 없어서 비교가 생략됐다면 ‘시각 회귀 통과’라고 쓰지 않는다. 새 기준선 커밋이 생기면 실제 PR head에서 CI를 다시 확인한다.

병합 전 base가 변경되거나 공유 컴포넌트가 다시 수정되면 영향 검사를 다시 한다. 체인 PR은 앞 PR의 수정분이 중복 반영되지 않았는지 비교하고 타입 검사한다. 파일당 충돌이 없다는 이유만으로 의미 충돌도 없다고 간주하지 않는다.

‘내부 데모 검증 통과’, ‘고객 확인’, ‘실운영 검증’은 별도 상태다. 현재 mock 기반 데모의 최종 판정은 내부 데모 준비 수준까지 입증하며, 실제 인증·장비 통신·영상 보존을 완료했다고 표시하지 않는다.

## 11. 고객용 문서와 최종 인계

고객용 문서는 **진입+업무 화면 6종을 7개 장면**으로 보여준다. 각 장면은 실제 구현 캡처·사용자 질문·주요 행동·다음 이동을 중심으로 구성하고, 필요한 PC/폰 비교를 곁들인다. ‘7장면’은 고정 PDF 7페이지를 뜻하지 않는다. 가독성이 떨어지면 설명·PC/폰 예시를 나눈다.

문서 생성은 원천의 소유주 데모 대상·spec·최종 캡처 매니페스트를 읽는다. 수기 화면 카탈로그나 별도 HTML 프로토타입을 제품 구현의 원천으로 만들지 않는다. 원문 셀 대응·미결·시연용 데이터 안내는 부록으로 두고, 내부 계정·개발 코드·테스트 결과표를 제품 화면에 노출하지 않는다.

기존 `pnpm docs:set`·`pnpm docs:check`는 전체 문서 세트 검사다. OD-12에서 owner 선택 생성 및 동등한 문서/캡처 정합 검사를 추가하고 실제 실행 명령을 기록한다. 정식 계약 세트도 함께 바뀌는 경우에는 원래 전체 문서 생성·정합 검사를 별도로 실행한다. `set_version` 승격과 고객 발행은 내부 초안 생성과 구분한다.

PDF는 파일 생성 성공만으로 통과하지 않는다. 모든 페이지를 렌더해 한글·화면·표·페이지 넘침·잘림·버튼/문서 내용의 식별성을 확인한다. PDF가 필요한데 생성기가 생략하거나 실패하면 해당 산출물은 미완료로 보고한다.

최종 인계 묶음:

1. 검증한 빌드/SHA, 실행 방법, 소유주 진입 URL, 데이터·시간 재현/초기화 방법.
2. 고객 검토용 문서와 5분 과제 대본, 동일 빌드의 PC·폰 캡처.
3. AC·검증 매핑 결과, CI/로그/trace/리뷰 판정, 남은 제약·미결 DISC.
4. 공개 시 확인할 URL·라우트 새로고침·파일/미디어 응답·PWA 갱신, 이전 빌드로 복구하는 절차.
5. 실제 고객 과제 수행 기록. 수행 전에는 ‘미실시’로 남김.

## 12. 계획 자체의 검토와 현재 상태

| 점검 | 이번 계획의 처리 |
|---|---|
| 기능만 나열한 계획인가 | OD별 선행·수정 대상·AC·게이트·증거를 연결 |
| KPI·텍스트·로그인 개선이 빠졌는가 | 공통 패턴·각 화면 AC·진입/현황 작업·시각 기준에 포함 |
| 소유주 의견이 설계 순서를 바꾸었는가 | 장비 찾기·계약/담당자·정보 시각·원문을 첫 과제로 채택 |
| PC만 통과하고 모바일을 완료로 셀 수 있는가 | WEB 작은 폭과 A4 PWA를 독립 검사, 대상 누락 실패 |
| 캡처와 코드 테스트가 서로 증명하지 못하는 부분이 있는가 | 일반 세션·스코프·미디어 본문·112 기본 시각 조합·과제 검토를 별도 층으로 구성 |
| 외부 결정이 전체 작업을 막는가 | 시연 기준안과 실제 운영 결정을 분리하고 해당 기능만 대기 |
| 초록색 검사와 고객 만족을 혼동하는가 | 내부 검증·실제 고객 확인·실운영 검증을 별도 상태로 관리 |

현재 작성·검토한 것은 계획이다. OD-00~14의 제품 구현·추가 검증 도구·112조합 캡처·고객 과제는 앞으로 실행한다. 날짜와 AI 실행 시간을 확정 일정으로 약속하지 않는다. OD-00에서 기준선과 작업 크기를 확인한 뒤 작업별 예상/실제 소요와 차단 원인을 PLAN에 기록한다.

### 이번 계획 작성의 검증 기록

- `node tools/ssot/check.mjs --docs` exit 0 — `✓ ssot: docs 106 · errors 0`.
- `node tools/ssot/check.mjs --specs` exit 0 — `✓ ssot: specs 15 · errors 0`. 기존 명세 정합 검사이며 새 `owner-experience` 명세를 작성한 것은 아니다.
- `git diff --check` exit 0. 계획 내 작업 15개·AC 18개·검증층 12개·게이트 9개 및 선행 작업의 존재·순서·문서 공백 검사 통과.
- `pnpm verify` exit 0 — 마지막 출력 `✓ DY: tokens 624 · contrast 94/94`. 이번 문서 변경 후 기존 저장소 게이트를 확인했다.
- 새로운 owner e2e·112조합 캡처·고객 검토는 이번에 실행하지 않았다. 위 계획의 앞으로 수행할 검증과 구분한다.
