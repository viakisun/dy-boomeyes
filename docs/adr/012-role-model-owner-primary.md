# ADR-012 — 역할 모델 재편: 소유주가 주인공, DY는 제조사 (Accepted 2026-09-11 — 사용자 승인 3회 · 리뷰 머지 가능)

## 맥락
`INTENT.md` §1이 "**운영사(DY)가** 전국에 임대한 CPB를 **관제하고**"로 시작했고, §2는 DY를 "운영사(보유·임대·정비·관제)"로, 소유주를 **2단계 제안 제3자**(DISC-026, "차사장 중기")로 갈라놓았다. `control` 페르소나는 "이관제 · 관제실 대형 모니터 **상시**"였다. 시연 대본 장면 1·4·9는 `control01`이 주인공이고, 장면 6(에스컬레이션)은 계정은 `hq01`(본사 안전관리자)이지만 B1-04를 거친다.

사용자가 2026-09-10~11에 세 번에 걸쳐 정정했다:
1. DY는 관제를 담당하지 않는다. 관제는 소유주·건설사(안전관리자)가 각자 범위에서 한다. DY는 전국을 볼 수 있지만 틀어놓고 감시하는 주체가 아니다 — 전국 운영 상태 대시보드 정도가 적절하다.
2. 소유주는 전국 영업을 한다("우리 CPB를 현장에 불러달라"). 그 영업 도구로 건설사에 관제를 제공한다. 100대 이상을 보유하고 현장관리를 해야 하는 소유주의 업무 편의가 핵심이며, **이 시스템의 원 의뢰자는 소유주**다.
3. DY는 소유주가 아니다. **DY는 제조사**이고, 소유주는 **DY CPB를 다수 구매해 보유한 회사**다. 소유주는 PC와 폰을 둘 다 쓴다.

이는 DY 자료와도 맞는다 — V5 3-9는 앱을 "CPB 회사용 · 건설사 안전관리자용" 두 종으로 적었고, 경진대회 자료 §2는 관제를 "고객 니즈"로 두며, 원본 RFP-021은 「CPB 회사」를 말한다. DISC-026 baseline의 "DY는 플랫폼·관제·정비"가 잘못된 전제였다. 우리가 DY 자료를 보고 방금 등록한 FR-039(가동률·타설량)·FR-043(단말기 탈부착·통신비)이 정확히 소유주의 빈칸이라는 점이 방증이다.

## 결정
사업 구조를 **3층**으로 고정한다: **제조사 DY → 소유주(중기업체) → 건설사(임차·현장 안전)**.

| 주체 | 하는 일 | BoomEyes에서 |
|---|---|---|
| DY (제조사) | CPB 제조·판매 · AS 정비 · BoomEyes 제공 · 전국 운영 데이터 열람 | B4 백오피스 · **B1 전국 뷰(읽기 위주)** · 정비 연계 |
| 소유주 (중기업체, **원 의뢰자**) | DY CPB 다수 구매·보유(100대+) · 전국 임대 영업 · 투입 요청 승인·배정 · 운전자 배치 · 계약 | **B1 운영 WEB(PC) + A4 PWA(폰)** · 보유 호기 스코프 |
| 건설사 (본사·현장) | 소유주에게 임차 · 현장 안전관리 책임(법적) | A1/A3 · B2/B3 · 자사 범위 — **소유주가 제공하는 상품** |
| 운전자 (소유주 소속) | 배정 장비 1대 | A2 |

- **`owner`는 2단계 제안이 아니라 1단계 주인공**이다. 표면은 A4(폰) + B1(PC). B1의 8화면 — 대시보드(지도·이상 장비·알림) · 수신함(투입 요청 승인) · 에스컬레이션 · 서류 · 임대 계약 · 이벤트 복기 — 는 100대를 임대하는 소유주의 PC 업무다. 특히 B1-03 수신함의 승인은 A4-03과 같은 일이다.
- **`control`은 "DY 제조사 전국 운영 뷰"로 재정의**한다. 같은 B1을 전국 스코프·읽기 위주로 본다. 관심사는 전국 가동률·이상 추이·부품 수명(AS 판매)·모델별 고장이지 개별 호기 대응이 아니다. 상황실 상시 감시 페르소나는 **없다**.
- B1 스코프는 `Scope.ownerId`로 가른다(`devScope`가 이미 지원). 7 페르소나 수는 유지한다.
- 시연의 척추는 장면 9 "사업 가치 — 임대 만료 → 재배치 → 홍보 → 추가 일거리"(소유주의 이야기)이며, 9/30 시연 메시지는 "DY가 관제한다"가 아니라 "**소유주가 전국 사업을 관리하고, 현장에는 관제를 제공한다**"다.

## 대안
| 대안 | 왜 아닌가 |
|---|---|
| 현행 유지(DY 상황실 관제, 소유주 2단계) | DY 자료·사용자 정정과 어긋남 · 원 의뢰자가 부록 |
| DY = 소유주로 합침 | 사실과 다름 — DY는 제조사, 소유주는 구매자 |
| `control` 삭제 | DY가 전국 운영 데이터를 볼 필요는 있음(AS·부품·모델 개선) |
| 소유주 전용 PC 표면(B5) 신설 | B1 8화면이 이미 그 일을 함 — 이름표와 스코프만 바꾸면 됨 |

## 결과
- 얻는 것: 원 의뢰자가 주인공이 되고, DY 자료(V5·경진대회·9/9)와 SSOT가 같은 그림을 그린다. 새 화면 없이 재배치로 끝난다.
- 잃는 것: `INTENT.md` §1~3 · `roles.yaml` · 시연 대본 1·4·9(+6 재검토) · B1 표면 이름 · 웹 로그인 카드가 바뀐다.
- 이 ADR과 함께 `roles.yaml` owner `surfaces`를 `[A4]` → `[B1, A4]`로 바꿨다. **문서용 변경**이다 — 접근 제어는 `screens.yaml`의 화면별 `roles:`를 `canAccess`(`packages/domain/src/session.ts`)가 읽으므로 B1 8화면의 `roles: [control, maintenance]`가 바뀌기 전엔 owner가 B1에 들어갈 수 없다(후속 1). 계약 ACC-110 "PC 상황실 관제 화면"의 운영 주체를 DY 확인으로 정리해야 한다(DISC-060).
- 되돌리려면: 이 ADR을 Superseded로 두고 `INTENT.md` §1~3·`roles.yaml`을 되돌린다.

## Rules
- [ ] 화면·문서에 "DY가 관제한다"는 서술을 쓰지 않는다. B1의 주인은 소유주다.
- [ ] DY의 전국 뷰는 읽기 위주다 — 승인·접수·호출 같은 조치 버튼은 소유주·현장의 것이다.
- [ ] 관제 기능은 소유주가 건설사에 제공하는 상품이다 — 건설사 표면(A1/A3/B2/B3)을 설계할 때 "누가 이걸 팔고 있는가"를 잊지 않는다.
