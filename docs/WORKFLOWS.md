# WORKFLOWS — 트리거별 업무 흐름 카탈로그

원천 `ssot/scenarios.yaml workflows[]` → 생성 표 [generated/WORKFLOWS.md](generated/WORKFLOWS.md). 이 문서는 읽는 법과 갱신 절차만 적는다.

## 1. 무엇인가

트리거(센서·사람·기한) 하나가 여러 역할을 가로지르며 업무가 되고 조치로 닫히는 흐름 18건. 묶음은 장비 이상 3 · 영상·AI 6 · 사람·현장 2 · 부품 2 · 서류 1 · 운영·계약 4.

[DEMO.md](DEMO.md)의 시연 대본이 25분 선형 순서라면 이 카탈로그는 사건 종류별 사슬이다. 대본은 계약 검수(ACC-1xx)와 묶여 있어 이 카탈로그가 바꾸지 않는다. 겹치는 흐름은 `scene` 열로 장면 번호를 가리킨다.

`ops[]`(생애주기 52행)와의 차이: `ops[]`는 개설 → 운영 → 종료 시간축의 행위자별 절차, `workflows[]`는 사건 하나가 흐르는 사슬이다.

## 2. 상태 표기

| 표기 | 뜻 |
|---|---|
| 화면으로 재현 | 지금 화면과 상태 데이터로 클릭하며 보여줄 수 있다 (14건) |
| 상태 데이터 필요 | 화면은 있으나 그 상태를 만드는 데이터나 조작이 없다 (2건 — WF-04는 점검 요청 액션 부재, WF-11은 신규 상태 데이터 부재) |
| 제안 | 2단계이거나 결정 대기 · 화면이 없을 수 있다 (2건 — WF-16 · WF-17) |

`phase`는 계약 단계이고 `status`와 별개다. 2단계 기능이라도 목업으로 보여줄 수 있으면 "화면으로 재현"이다(WF-07 · WF-09 · WF-12).

## 3. 목업이 실제로 하는 자동화

목업은 규칙 엔진이 아니다. 코드가 스스로 하는 것은 셋뿐이다 — 서류를 제출하면 검토 업무가 생기고, 현장 신고가 업무와 알림을 만들고, 에스컬레이션 화면을 열 때 1시간 미접수 업무가 통보 상태로 넘어간다. 나머지 알림·업무 연결은 시드 데이터에 결과로 들어 있다. 실 인입과 자동 발행은 웨이브 3(실연동).

## 4. 드러난 빈칸 (이번에 고치지 않고 표기만)

| 빈칸 | 근거 | 표기 위치 |
|---|---|---|
| 알림 3종(사람 접근 후보 · 카메라 상태 · 현장 신고)의 수신 역할 미정 | B4-05 기준표는 8종만 정의 | WF-05 · WF-07 · WF-08 `notify: []` · DISC-050 |
| 기한 초과 시 본사 통보 미구현 | ENT-06 규칙에는 있음 | WF-02 비고 |
| 정비 담당 전용 화면 없음 (조치 보고 채널) | DISC-035 미결 | WF-01 · WF-04 비고 |
| 임대 만료는 알림 기준표에 없음 | B1-06 | WF-14 비고 |

## 5. 갱신

`ssot/scenarios.yaml workflows[]` 수정 → `pnpm ssot:check` → `pnpm ssot:build` → 생성 표까지 커밋.

검사가 막는 것: 화면·참조 ID 실존 · `notify` 역할 실존 · `screens`와 `steps[].screens` 합집합 일치 · `scene`이 `demo[]`에 실존 · 본문 5필드(`title` `trigger.what` `steps[].do` `today` `gain`)의 내부 식별자와 금지어(사건 · 조치 요청 · 소모품 · 구현 용어). 본문은 고객 언어로 쓴다.
